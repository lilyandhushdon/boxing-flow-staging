1. Overview

Boxing Flow is a boxing training web app. It began as a round timer with a 3D coach who demonstrates combinations, and has grown into a training companion: guided boxing and conditioning sessions, mental skills, a training calendar, a fight-camp planner, a nutrition diary, film study, and heart-rate monitoring. Everything is remembered in the person's own account and follows them across devices.

Who it is for

Boxers and boxing fans training alone or alongside a coach. At the moment it has one user (the owner) and is not public.

What it is made of

A static website of plain HTML and JavaScript (no build step), a few Netlify Functions, and a Supabase project (Postgres and sign-in) for accounts and saved data.

Where it runs

Any modern browser, phone first. Hosted on Netlify at heroic-jalebi-e2e04b.netlify.app. Source on GitHub at lilyandhushdon/boxing-flow-staging (branch main).

Status of the live site

The Netlify site is not connected to the GitHub repository: its last deploy was on 10 Oct 2026 and pushing to GitHub does not update it. To publish, run netlify deploy --prod from the project folder, or link the repository in Netlify (Site configuration, Build and deploy). See section 9.

2. Architecture

The app is local first. Every screen reads and writes the browser's own storage, so it is fast and works offline. A sync layer copies those saves to the person's Supabase account and brings changes from other devices back. Food search goes through one Netlify Function so the USDA key never reaches the browser.

Key ideas

  • No build step. The files in the repo are the files that are served (publish = "."). Scripts are classic scripts sharing global names, not modules (except the 3D coach script).
  • Local first, sync second. Modules never talk to the database for settings or progress: they call localStorage as before, and cloud.js notices. Only the nutrition diary talks to Supabase tables directly.
  • One server function. /api/foods merges two food databases and keeps the USDA key private.
  • The database protects itself. Every table has row level security, so even though the Supabase key in the page is public, one person's rows cannot be read or changed by anyone else.

4. How the app is built

Screens and routing

The app is one page. Each screen is a <section id="..."> and show(id) hides all the others, stops anything that should not keep running (breathing animation, the live channel, the film study video, the 3D gym), and calls the screen's render hook.

Deep links

Open app.html?go=NAME or app.html#NAME?params. The router (route()) understands:

  • Screens: today (or dashboard), explore, modes (or boxing), strength, mind, calendar, camp, film, nutrition, weight, hr (or heartrate), breath, reframe.
  • Workouts: coach, basic, timer, scenario, output, plyo, shoulder, treadmill, iq.
  • Choices (numbers pick an entry in that list, checked against its length): focus (comma list of drill ids), opt, preset, scen, sopt, out, oopt, plyo, popt, shd, shopt, tm.

Navigation rule

Back links show only when someone arrived through a hub page (hubClick sets the body class from-hub); the Boxing and Strength hubs have no back link; other screens link back to the Dashboard. The logo in the top bar always goes to the Dashboard. The top bar and burger menu are hidden during a workout.

Preview iframes

The dashboard's quick workout widget and the Boxing card embed index.html?preview in an iframe to show the live coach. Each iframe has a data-on screen, is loaded only while that screen is visible (syncPreviews), sends a bfAlive heartbeat, and is reloaded if the heartbeat stops. A static ring placeholder shows until it is ready.

5. Features

Dashboard

Code: home.js. Screen: today, the app's home.

  • Widgets in default order: today, weight, camp, nutri, quick, live, film, minical, week, progress, suggest, recent, explore. Each widget is a persistent element refreshed in place and positioned with CSS order, so the live coach preview and the live channel never reload when the dashboard refreshes.
  • Rearranging: press and hold a widget and drop it on another to swap places. The order is saved in bfWidgets (and so syncs). "Reset layout" removes the key.
  • Header badges: this morning's weight and what is left to the fight weight (tap it for the weight screen), and next to it, days until the fight (from the training camp), with weeks and days beneath. For the starter camp (no fight date) it counts to the end of the camp and says "days of camp left". After the camp ends it shows the day streak.
  • Progress comes from the session log (bfLog, last 500 sessions): streak, sessions and minutes this week, a weekly goal (bfGoal, 1 to 7).
  • Suggestions pick the area (boxing, strength, mind) done least in the last two weeks and the way to train in it done least recently.

Boxing training

Code: the main script in app.html plus the content data files. All workouts run through one engine: a list of steps (round, rest, warm-up...) with durations, played by a timer loop with Web Audio tones, spoken callouts (speech synthesis), optional music and crowd sound, and the ring display.

ModeWhat it does
Coach workout (coach)The 3D coach demonstrates drills round by round. Pick skills (FOCUS list) and the round format. Includes interactive gym mode, a male and a female coach, and a finale where the drills are celebrated.
Basic workouts (basic)Fixed workouts without the 3D coach, including the Attacking and Defence drills, sorted A to Z.
Round timer (timer)Plain rounds and rests.
Fight scenarios (scenario)Five opponent styles, each a five-round plan. Every round is five one-minute phases with three coaching points at 20 second intervals, plus encouragement phrases. Three-minute and five-minute round options.
Output rounds (output)Punch-volume targets of 90, 135, 210, 270, 360, 400 and 500 punches, plus 540 "three-punch blocks", called out like a coach would ("x2", "x3").
Boxing IQ (iq)96 scenario questions (four options, one answer, an explanation, a difficulty) in 12 topics. Scores in bfIQ.

3D coach: single source of truth

Two tables in app.html decide everything the coach shows. The drill list (FOCUS) lists each drill's moves in order; the move library (MOVE_LIBRARY) names the one animation file for each move. The README holds the move-to-file table. The 3D coach is three.js 0.160 loaded from jsDelivr; if WebGL or a file fails, an illustrated coach remains.

Phone behaviour

A silent looping audio element of matching length plus the Media Session API gives lock screen controls and a correct progress bar on iPhone, and keeps audio alive in the background. A wake lock keeps the screen on. The iPhone gold-square countdown bug (a compositing glitch) was fixed; the 360-degree spin was kept.

Finishing a session

When a session ends its finish screen shows a Save workout step with an optional label and notes. Nothing is recorded until Save is pressed (offerSave in the main script keeps the pending session; the end screens of workouts, the 3D finale, breathing, reframing and the quiz all use it). Saving calls sessionDone({type, minutes, planId, label, notes}) in calendar.js, which:

  • writes a log entry (bfLog) with the label (custom), notes and a readable title such as "3 x 3 sparring rounds · Round timer · 3 rounds of 3 min";
  • ticks the planned session off the calendar: the one it was started from, or otherwise today's not-yet-done planned session of the same kind (exact same choices first);
  • copies the label and notes onto that planned session, and refreshes the dashboard straight away so the Today, Progress, Week, Do it again and calendar widgets are current without navigating.

The label can also be typed beforehand: on the setup screen of the plain workouts (the round timer especially, "Label this session") or when planning in the calendar. Notes and labels are saved inside bfLog and bfPlan, so they sync to the account like everything else.

Strength and conditioning, and mental skills

  • Plyometrics (plyo.js): bodyweight, lower-body, upper-body and medicine-ball libraries with a different set of moves each round, with coaching tips.
  • Shoulder conditioning (shoulder.js): a drill and an 8-minute shoulder burner.
  • Treadmill intervals (treadmill.js, mode treadmill): five advanced running workouts from Red Zone Running, all at a 1.5% gradient: Norwegian (22 min), Brianstorm (20), Crying Lightning (36), Sharpshooter (39) and Apples & Pairs (30). A workout is a list of loads; a load is a pattern of on and off intervals (for example 30 seconds on, 15 off, 4 times) at a speed range in km/h, with a recovery after it, and the whole list can repeat (Crying Lightning four times, Sharpshooter twice). The timer screen shows the load and rep, the interval's own countdown in the big number, the speed to run, and the time left in the load; the voice calls "Load 2, 20 seconds on, 10 off, 6 times, on, 17 to 19", then just "Off." and "On."; a bell starts each load and a beep marks each change. Each load is one "round" for the progress bars and the up-next list. The Brianstorm sheet does not print its recovery times: 2 minutes after each load is what makes it the 20 minutes it is named for. A test checks that every workout's loads add up to its stated minutes.
  • Mental skills (mind.js): box breathing with an animated guide and adjustable minutes, cognitive reframing, and read-through skills.

Training calendar

Code: calendar.js. Data: bfPlan.

  • Week and month views. Add, edit and delete a planned session (any way of training from the WAYS table: coach, basic, timer, scenario, output, IQ, plyo, shoulder, breathing, reframing, rest day). Repeat options.
  • Press and hold a session to move it to another day (holdDrag). Tap to start it; finishing ticks it off.
  • Export to .ics for any calendar app.
  • Every session can have a label ("Heavy bag, jab and double jab") and notes. The label shows first in every list ("Heavy bag · Round timer · 3 rounds of 3 min"); the notes show when the session is opened. Starting it from the calendar carries the label into the workout, and saving the workout writes its label and notes back.
  • If a training camp exists, the calendar shows which phase and focus block each day is in (coloured strip and tints).

Training camp

Code: camp.js. Data: bfCamp, bfCampInfoSeen.

  • A camp is split into four phases, Base, Build, Peak, Fight week, and each phase into two-week focus blocks. Each block has a goal (written by the app, editable) and tasks with subtasks that can be ticked, added and deleted. Many tasks link straight into a workout ("Practise").
  • Starter camp: an 8-week camp from today is created automatically, so there is nothing to set up. "Change length or fight date" rebuilds it, keeping ticks, edited goals and custom tasks where the new camp has the same task.
  • Lengths: 6, 8, 10 or 12 weeks (SHARES gives the weeks per phase). If the fight is sooner than the camp, the camp shrinks proportionally and low-priority tasks are trimmed (allocate uses largest-remainder rounding with minimums).
  • The camp does not schedule workouts. It gives a two-week focus (coach feedback, the person's own ideas) to keep in mind when planning sessions. A "how your training camp works" explainer opens the first time.
  • The dashboard widget shows the current phase, the focus goal and the next open tasks, with ticks.

Weight

Code: weight.js. Data: bfWeight (saved on the device and synced like everything else): {entries: [{d, kg, note}], target: {kg, date}}, one entry per day. Screen: weight (menu, ?go=weight, or tap the weight on the dashboard).

  • Log: a weigh-in for any day (default today) with an optional note, from the dashboard widget's quick box or the weight screen. Tap a history row to change it. Weights outside 30 to 300 kg are refused as typos; nothing else is limited.
  • Fight weight: set it as a weight, or as "kg to lose from now" (this morning's weight minus that), with a weigh-in date (empty means the training camp's fight date). There is no limit on how much or how fast: a water cut is a normal part of fighting and the plan is between the fighter and their coach, so the screen only shows the numbers: kg to lose, days to weigh-in, kg a week needed, and that as a percentage of body weight.
  • What it works out: this morning's weight and the change since the last weigh-in; the 7-day average (one weigh-in moves a kilo or more with food, water and salt); the change over about a week; the lowest, highest and number of weigh-ins; the pace over the last two weeks (a straight line through the weigh-ins, needs three over four days); and where that pace lands on weigh-in day.
  • Chart: weigh-ins, the 7-day average, the fight weight as a dashed line, and the projection to weigh-in day.
  • Dashboard: a weight badge beside the fight countdown in the header (this morning's weight, and kg to go) that opens the weight screen, and a Weight widget with the weight, what is left, a two-week line and a quick log box.
  • Nutrition link: one weight, not two. Nutrition's settings take the weight from this log, and a weight typed there is added to it. When the log's weight has moved 0.5 kg or more from the weight the calorie targets were worked out at, the nutrition screen offers "Update my targets" (never automatically, and not if the targets were set by hand).

Nutrition

Code: nutrition.js, netlify/functions/foods.mjs. Data: Supabase tables (not localStorage).

What the person can do

  • No separate sign-in: on this computer the app signs in automatically (owner mode, section 8). Without that, the nutrition screen shows a temporary email and password form (or an email link) until the whole app has its own sign-up. Pick a day (previous, next), add food to Breakfast, Lunch, Dinner or Snacks: search by name, choose an amount in grams or a serving ("1 large banana"), and add. Edit the amount or delete an entry. "Copy yesterday's meals".
  • Scan a barcode (Chrome on Android and desktop; elsewhere a typed barcode), quick-add calories and macros, create their own foods, see recent foods and their own foods before typing.
  • Daily summary: calories left (or over), and protein, carbohydrate and fat bars against targets. Targets are worked out from sex, age, height, weight, training level and goal with the Mifflin-St Jeor formula; the pace of weight change is capped (never more than 20% below maintenance, never below a minimum). Protein is 2.0 g per kg (2.2 when cutting), fat 25% of calories, carbohydrate the rest. The person can override every target. Energy can be shown in kcal or kJ.
  • A weight-cut warning is shown: this is a guide, not medical advice.

The food search function

RequestResult
/api/foods?q=weetbixUp to about 25 foods in one shape: {id, source, generic, name, brand, per100:{kcal,protein,carbs,fat,fibre,sugar,sodium_mg}, serving:{label,grams}|null, nz}, nutrients per 100 g. partial:true means one database failed. searchedAs tells the page that a New Zealand word was translated.
/api/foods?barcode=9400...One packaged product, or item:null.
/api/foods?usda=173944The serving sizes for one USDA food (1 large banana = 136 g...).
  • Order: everyday USDA foods first, then New Zealand products from Open Food Facts, then packaged USDA, then other Open Food Facts products.
  • New Zealand: Open Food Facts is searched twice, once limited to New Zealand products, so NZ items always appear. NZ words are mapped for USDA (mince is ground beef, kumara is sweet potato, capsicum, courgette, coriander, prawns, biscuits, crisps, silverbeet, beetroot, yoghurt, porridge, lollies, and so on). USDA's own branded list also contains some NZ products.
  • Ranking: USDA everyday foods and packaged foods are searched separately (or packaged ones crowd out plain ones), then ranked by how many search words match, whether the name looks unusual (dried, powder...), and shortness.
  • Caching: successful responses are cached for a day (a week for serving sizes) at the Netlify edge. Failures are not cached.
  • Entries keep a snapshot: each diary entry stores the food's nutrients per 100 g and the grams, so editing the amount recalculates, and old entries never change if a database changes.

Dashboard widget

Shows calories left, macro bars and an "Add food" button, or a sign-in prompt. It paints at once from a small cache (bfNutriCache) and updates when the account answers.

Film study

Code: film.js, fighters.js. Data: bfFilm.

  • Paste a YouTube link (watch, short, shorts, embed, live and mobile links, with an optional start time) and it plays in the page using YouTube's own embedded player (IFrame API).
  • Pausing opens a note stamped with that moment (a short delay stops scrubbing counting as a pause). "Add note at this moment" works without pausing. Tap a note's time to jump to it. Edit and delete notes; add key takeaways; copy all notes (with time-stamped links) as text.
  • The library lists studies with thumbnails; reopening resumes where the person stopped.
  • Fighters: "Study a fighter" lists 45 fighters (A to Z), each with their full fights from official channels (336 fights). Tapping a fight opens it with the link already filled in. The data is in fighters.js as ['Opponent', 'videoId', 'Channel'], one line per fight.
  • How fights were chosen: only full fights on official channels (Top Rank, DAZN, Matchroom, Premier Boxing Champions, Golden Boy, Sky Sports Boxing, The Ring, BOXXER), found by searching YouTube and then checking each with YouTube's oEmbed check (HTTP 200 means embedding is allowed). Highlights, marathons and fan uploads were excluded. Videos can be removed later, so the list should be re-checked (see section 10).
  • Dashboard widget: a fight to study (a different one each day, or "Another fight"), plus "carry on" with the last study.

Limits: some videos block embedding (the page says so and links to YouTube); on iPhone playback needs a tap and stops when the screen locks.

Heart rate

Code: hr.js. Data: bfHR (age and max heart rate).

  • Connects to a chest strap (tested design for the Polar H10; also Garmin straps and any strap using the standard Bluetooth heart rate service) through Web Bluetooth. Shows live beats per minute and the training zone.
  • Reads the standard Heart Rate Measurement packet: 8-bit or 16-bit beats per minute, and beat-to-beat (RR) intervals, kept for later recovery and HRV features.
  • Zones as a share of max heart rate: Easy 50%, Aerobic 60%, Tempo 70%, Hard 80%, Max 90%. Max heart rate is the person's own number or estimated as 208 - 0.7 x age (Tanaka).
  • A heart pill with the bpm, coloured by zone, shows at the top of the workout timer. If the strap drops, it retries for about a minute. Stale readings show dashes.
Platform limit

Web Bluetooth does not exist in Safari or any iPhone or iPad browser. It works in Chrome and Edge on Android, Windows, Mac and Chromebook, and in the Bluefy browser on iPhone. Supporting the iPhone properly needs a native wrapper (see roadmap). The page needs HTTPS (or localhost).

Live boxing channel

Code: home.js (the live widget). A dashboard widget that plays Boxing World TV (boxingworld.com), a free 24/7 boxing channel, in a frame. It loads only when "Watch free boxing now" is tapped, shows the site as they serve it (their player, ads and cookie banner), and stops when the dashboard is left or "Stop" is pressed.

Licence

Their terms allow personal, non-commercial use and forbid redistribution without permission. This is acceptable for the single owner only. Before the app is public or paid, get written permission (a draft email to the channel is in the project history) or replace the widget with a plain link. TrillerTV, FITE, Tubi, Roku, Plex, XUMO and Rakuten TV all block framing and cannot be embedded.

It has a hero with the live coach preview, the feature sections (including "Beyond the bag"), a coach card that opens the coach workout, a burger menu mirroring the app's, and card links of the form app.html?go=.... With ?preview it renders as an embeddable preview (used by the dashboard). The pricing and paywall links were removed while payments are paused.

What is in the database

How sync works (cloud.js)

  1. Noticing changes. Storage.prototype.setItem and removeItem are wrapped. A write to a synced key records the time in bfSyncMeta.ts[key] and schedules a push 0.3 seconds later (so a burst of edits goes up as one). This is why cloud.js must load first.
  2. Pushing. Keys whose change time is newer than the last pushed time are upserted into app_data with that time as updated_at. A removed key is sent as deleted = true. On failure the keys stay marked as changed and a retry runs after 15 seconds and when the device is back online.
  3. Closing the page. When the page is hidden or closing, changes not yet sent go straight to the database API in a request the browser finishes by itself (keepalive), so changing something and refreshing at once does not lose it. (Over about 60 KB it falls back to the normal request.)
  4. Pulling. On sign-in, every 30 seconds while the app is open and visible, when the page becomes visible again and when back online, all rows are read. For each key the newer side wins. Keys that exist only on this device are sent up.
  5. First link of a device to an account. A device that has never been linked to this account (including when a different account signs in on it) takes the account's version of every key the account has, whatever the timestamps. This stops a new phone's starter data (for example an automatically created starter camp) from overwriting the real thing. Data that exists only on the device is never deleted: it is sent up to the account.
  6. Nothing is lost silently. Before an update from the account replaces this device's copy of a key, that copy is kept in bfSyncMeta.backup. The menu then offers "Undo the last update from your account" (bfCloud.restoreBackup()).
  7. Applying changes. The modules hold what they loaded in memory, so new data needs a restart. Right after the page opens (within 15 seconds, not mid-workout, not more than once per 20 seconds) the page reloads itself; later, a bar at the bottom says "Your data was updated from another device" with a Refresh button.

The bottom of the menu has a status line (#syncLine): "Saved to your account, last at 10:32" with Sync now; "Saving..."; "Not signed in: your data is only on this device" with Sign in; or the reason a save failed with Try again. It is the first place to look if something does not seem to be saved.

Conflict policy

Last write wins, per key. If two devices edit the same key (for example the calendar) while apart, the later save replaces the other. That is fine for one person on one device at a time. If it becomes a problem, merge by item (plan entries and film notes have ids) instead of by key.

Status for the interface is in bfCloud.status (and bfCloud.error): off, syncing, ok, offline or error.

Current state

Better: in Netlify, Site configuration, Build and deploy, link the GitHub repository and set the production branch to main, so every merge deploys. With the CI plan below, deploys then happen only when the checks pass.

11. Security and privacy

  • Row level security on every table; verified with a second account and a logged-out visitor (neither can read, change, delete or forge rows). New tables must follow the same pattern.
  • Keys: only the public anon key is in the page. The service key and DB password stay in .env. The USDA key lives in the Netlify function. Rotate any key that was ever pasted into a chat or document.
  • Personal data: email address, body measurements, heart rate settings and food diary are health-related. They are stored only in the person's account and on their device. A privacy policy and terms are needed before the app is public; the nutrition screen already carries a "not medical advice" note and a weight-cutting warning.
  • Sign-out leaves local data on the device; signing in as a different person clears the synced keys first.
  • Publishing: Netlify serves the whole folder (publish = "."), and a deploy made from this folder with the command line uploads every file in it, including the private .env. netlify.toml therefore answers a forced 404 for /.env, /docs, /tests, /supabase, /netlify, /.github and /node_modules, and a test fails if any of those rules is removed. Deploys that come from GitHub only contain committed files, which is another reason to link the repository.
  • Third-party content: only embeddable, official video sources; attribution for Open Food Facts; Boxing World TV for personal use only.

14. Decisions and why

DecisionReason
Plain HTML and JavaScript, no framework or buildFastest to change and deploy, nothing to break in a toolchain; the cost is global names and a very large app.html. Revisit if the code needs to be shared by a native wrapper or many contributors.
Local firstInstant, works offline in the gym; the account is a copy, not a requirement.
Supabase (Postgres) instead of MongoDBSign-in and per-user data protection are built in, so the browser can talk to the database safely without writing our own server; a Mongo setup would need our own functions and login. Postgres also scales to a real product and is portable.
Sync every bf key whole, newest winsZero work for new features and good enough for one person; item-level merging can be added later.
Nutrition in real tables, not blobsIt is queried (by day, totals, recent foods) and will want reporting.
Food data through one Netlify FunctionKeeps the USDA key private, merges two sources, adds caching and New Zealand handling in one place.
Official-channel full fights only in film studyAvoids dead links and copyright trouble; every link checked for embedding.
Training camp as a focus board, not a schedulerThe camp tells you what to work on for two weeks; the calendar remains the person's own plan.
Tests in tests/ with their own package.json, Playwright pinnedThe app has no build step and should not gain one just for testing; keeping the tooling in its own folder keeps the root clean and stops Netlify from installing it.
Browser tests replace every outside serviceFast, free and the same result every time; real services are checked separately (the weekly video check, and by hand).
Owner mode instead of a nutrition sign-inSign-in belongs to the whole app and will be built once with sign-up. Until then a private owner file signs the owner in on their own computer, so nothing asks for a login, without putting a password in a public page.
Sync never deletes this device's data, and keeps a copy of anything it replacesLosing a change is worse than a harmless leftover. Accounts can be switched without wiping the device, and an update from the account can be undone.
Save step on every finished sessionA session counts when the person says so, with a label and notes: the label is what tells a 3 x 3 round-timer session from another.
Paywall pausedAdd more features first; the code stays in the repo.
Email link sign-in (no password)Nothing to remember or leak; the same link creates an account.
